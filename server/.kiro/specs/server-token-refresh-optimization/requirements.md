# Server Token 自动刷新优化

## 概述

优化 Server 端的 token 自动刷新机制，借鉴 Kiro IDE 客户端的智能刷新策略，提升效率、可靠性和可观测性。

## 背景

当前 Server 端的 token 自动刷新存在以下问题：
1. 定时全量刷新所有账号，不检查是否即将过期，浪费 API 调用
2. 缺少账号状态管理，重复刷新已知失败的账号
3. 刷新后不同步账号信息，无法及时发现封禁状态
4. 缺少详细的刷新日志和健康检查机制
5. 配置更新需要重启服务

## 目标用户

- 后端服务运维人员
- 账号管理员
- 系统监控人员

---

## 用户故事

### 1. 智能过期检测

**作为** 系统管理员  
**我希望** 系统只刷新即将过期的 token  
**以便** 减少不必要的 API 调用，降低服务器负载

**验收标准：**
- 1.1 系统能够检查每个账号的 token 过期时间
- 1.2 只有在 token 过期前 5 分钟内才触发刷新
- 1.3 没有过期时间的账号在首次刷新后记录过期时间
- 1.4 刷新日志显示跳过的账号数量和原因

### 2. 账号状态管理

**作为** 系统管理员  
**我希望** 系统能够记录和管理账号的错误状态  
**以便** 避免重复刷新已知失败的账号

**验收标准：**
- 2.1 账号模型包含 `lastError`、`lastCheckedAt`、`consecutiveFailures` 字段
- 2.2 刷新失败时记录错误信息和失败次数
- 2.3 刷新成功时重置失败计数
- 2.4 跳过已封禁账号（lastError 包含 AccountSuspendedException）
- 2.5 跳过连续失败 3 次以上的账号
- 2.6 提供 API 重置账号错误状态

### 3. 刷新后同步账号信息

**作为** 系统管理员  
**我希望** token 刷新后自动同步账号使用量和订阅信息  
**以便** 及时发现账号封禁和使用量变化

**验收标准：**
- 3.1 token 刷新成功后自动调用 Kiro API 获取账号信息
- 3.2 更新账号的使用量、订阅类型、剩余天数等信息
- 3.3 检测到 423 状态码或 AccountSuspendedException 时标记账号为已封禁
- 3.4 同步失败不影响 token 刷新的成功状态
- 3.5 记录同步失败的详细日志

### 4. 刷新日志和历史记录

**作为** 系统管理员  
**我希望** 查看详细的刷新历史记录  
**以便** 分析性能问题和排查错误

**验收标准：**
- 4.1 每次批量刷新生成一条日志记录
- 4.2 日志包含：时间戳、总账号数、成功数、失败数、总耗时
- 4.3 日志包含每个账号的详细结果：邮箱、成功/失败、错误信息、耗时
- 4.4 提供 API 查询最近 N 次刷新日志
- 4.5 日志持久化到数据库或文件
- 4.6 自动清理 30 天前的旧日志

### 5. 健康检查和告警

**作为** 系统管理员  
**我希望** 系统能够主动监控刷新状态并发送告警  
**以便** 及时发现和处理异常情况

**验收标准：**
- 5.1 提供健康检查 API 返回系统状态
- 5.2 健康状态包含：总账号数、活跃账号数、封禁账号数、失败账号数
- 5.3 健康状态包含：上次刷新时间、下次刷新时间、告警列表
- 5.4 当封禁账号数 > 0 时生成 ERROR 级别告警
- 5.5 当失败账号数 > 总数 30% 时生成 WARNING 级别告警
- 5.6 支持通过 WebSocket 实时推送告警（可选）
- 5.7 支持邮件/Webhook 告警通知（可选）

### 6. 动态配置更新

**作为** 系统管理员  
**我希望** 更新刷新配置后立即生效  
**以便** 无需重启服务即可调整刷新策略

**验收标准：**
- 6.1 更新配置后自动重启调度器
- 6.2 新的刷新间隔立即生效
- 6.3 新的并发数立即生效
- 6.4 启用/禁用自动刷新立即生效
- 6.5 配置更新记录到日志

### 7. WebSocket 实时通知（可选）

**作为** 前端开发者  
**我希望** 通过 WebSocket 接收刷新进度通知  
**以便** 在前端实时显示刷新状态

**验收标准：**
- 7.1 刷新开始时发送 `refresh:start` 事件
- 7.2 每个账号刷新完成时发送 `refresh:account` 事件
- 7.3 批量刷新完成时发送 `refresh:complete` 事件
- 7.4 事件包含必要的数据：账号邮箱、成功/失败、错误信息
- 7.5 前端可以订阅和取消订阅事件

## 非功能性需求

### 性能要求
- 智能过期检测应减少至少 80% 的不必要 API 调用
- 单个账号刷新耗时不超过 5 秒
- 批量刷新 100 个账号（并发 10）耗时不超过 60 秒
- 健康检查 API 响应时间不超过 100ms

### 可靠性要求
- 单个账号刷新失败不影响其他账号
- 系统崩溃后能够恢复刷新状态
- 数据库操作失败有重试机制

### 可维护性要求
- 代码结构清晰，职责分离
- 关键操作有详细日志
- 错误信息清晰易懂
- 配置项有明确的注释说明

### 兼容性要求
- 向后兼容现有的账号数据结构
- 新增字段使用可选类型，不影响现有功能
- 提供数据库迁移脚本

---

## 技术约束

- 使用 TypeScript 开发
- 使用现有的 Express.js 框架
- 使用现有的数据库适配器（MySQL/JSON）
- 不改变现有的 API 接口签名（只增加新接口）
- 保持与 Kiro IDE 客户端的 API 兼容性

### P0 - 必须实现
- 智能过期检测（用户故事 1）
- 账号状态管理（用户故事 2）

### P1 - 应该实现
- 刷新日志和历史记录（用户故事 4）
- 健康检查和告警（用户故事 5）
- 动态配置更新（用户故事 6）

### P2 - 可以实现
- WebSocket 实时通知（用户故事 7）
- 邮件/Webhook 告警通知

## 成功指标

- API 调用次数减少 80% 以上
- 封禁账号在 5 分钟内被检测到
- 刷新失败率低于 5%
- 系统可用性达到 99.9%
- 问题排查时间减少 50%

## 风险和依赖

### 风险
- 数据库迁移可能影响现有数据
- 新增字段可能导致存储空间增加
- 频繁的状态更新可能影响数据库性能

### 依赖
- AWS OIDC API 的稳定性
- Kiro API 的可用性
- 数据库的读写性能
